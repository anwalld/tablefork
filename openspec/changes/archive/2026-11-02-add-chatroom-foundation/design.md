# Design

## Context

动机和范围见 `proposal.md`。仓库目前只有 Hello World，所有工程结构都是新建。

影响设计的约束：

- 第一阶段单实例运行，但产品按多实例公开服务设计，核心路径不能依赖单进程内存状态。
- Homebrew 版 Drogon 未启用 MySQL 和 Redis 支持，需要带 MariaDB Connector/C 和 hiredis 从源码构建。
- Drogon 1.9.13 的 Redis 客户端只接受固定地址，没有 Sentinel 支持。
- Drogon 1.9.13 在 MySQL 不可达时会在 `MysqlConnection::disconnect()` 中崩溃，需要打补丁。
- Drogon 的连接分布在多个 IO 线程上，房间连接表需要并发安全。

## Goals / Non-Goals

**Goals:**

- 消息提交后不丢失，同一房间内顺序一致。
- 单实例也走完整的跨实例广播路径，进入多实例阶段时无需重写消息主干。
- 后续 AI 成员复用同一成员模型和消息入口。
- 开发和部署使用同一份镜像，本地一键启动完整环境。

**Non-Goals:**

- Redis 自动故障切换。第一阶段不部署 Sentinel。
- 封号和踢人。第一阶段的发送权限只判断会话有效且是房间成员。
- 模型流式回复的消息形态，留到接入 AI 时设计。
- 大群场景。单房间写入上限由行锁决定，第一阶段不针对千人以上房间优化。
- 邀请链接、拒绝邀请和撤销邀请。
- 单独删除某个用户的消息。退出者的消息留给其他成员，直到房间被删除。

## Decisions

### 整体结构

```text
                  Vue client
                      |
                      v
                 Nginx (L7)
                      |
                      v
              Drogon app (1 instance)
               |              |
               v              v
             MySQL      Redis master --> Redis replica
```

### 消息路径

```text
client --> WS handler --> room worker --> MessageService
                                               |
                         BEGIN                 |
                           check membership    |
                           check client_msg_id |
                           last_seq + 1        |
                           INSERT message      |
                         COMMIT                v
                               +---------------+---------------+
                               |               |               |
                               v               v               v
                            ack sender    Redis hot cache   PUBLISH room:{id}
                                                               |
                                                               v
                                                  app pushes to WS clients
```

WS handler 只负责解析和校验格式。人类成员和后续 AI 服务都通过 `MessageService` 发消息。

### 消息先写 MySQL，再更新缓存和广播

提交成功即视为发送成功，MySQL 是消息的权威来源。缓存更新或广播失败只记录日志，不回滚消息。

备选方案是先写 Redis 再异步落库，延迟更低，但 Redis 主从复制默认异步，切换时可能丢失已确认的消息并回退序号。`WAIT` 能缩小窗口，但不能严格避免，且会增加延迟和配置复杂度。

### 用 MySQL 房间计数分配 `seq`

在消息事务内更新 `rooms.last_seq`，`seq` 在房间内连续递增，`(room_id, seq)` 建唯一索引，同时用于按房间查历史。

- Redis `INCR`：分配快，但写库失败有空洞，切换时序号可能回退，序号顺序也可能与提交顺序相反。
- 全局自增 ID：最简单，没有房间级热点，但不连续，无法从实时推送中发现漏消息，且提交乱序可能导致按游标补齐时漏消息。

### 按房间哈希到固定 worker

`hash(room_id)` 决定消息由哪个 worker 处理。每个 worker 严格串行，等当前消息提交后才处理下一条，因此每个 worker 最多占用一个数据库连接，高频房间不会耗尽连接池。

队列有长度上限，满时拒绝并返回可重试错误。worker 主要用于隔离连接占用，`seq` 的正确性仍由行锁保证，所以多实例后两台机器处理同一房间也不会出错。

备选方案是不做 worker，实现更简单，但等待行锁的事务会各占一个连接，房间之间会通过连接池相互影响。

### 广播走 Redis Pub/Sub

每个房间一个频道 `room:{id}`。实例在出现该房间的第一个连接时订阅，最后一个连接断开时退订。发送方所在实例同样通过订阅接收，不走本地捷径，这样单实例就在验证多实例路径。

Pub/Sub 不保证送达也不保留消息，发布顺序也可能与提交顺序不同，这些都由客户端按 `seq` 处理：

- 排序：收到不连续的 `seq` 时短暂等待，超时后拉历史补齐。
- 进入房间或重连：先订阅，再拉历史，然后按 `seq` 去重。
- Redis 连接恢复后，实例重新订阅本地所有房间。

连接建立后不会自动收到推送，客户端要逐个房间发送 `subscribe`，服务端校验成员身份后回复 `subscribed`。这样“先订阅，再拉历史”才有明确的先后。Redis 的订阅调用没有确认，所以实例向频道发布标记，收到后才回复；发布失败时立即回复，客户端照常拉历史，等 Redis 恢复后再补齐。

备选方案是进程内广播，第一阶段更简单，但跨实例路径要到后面才第一次被验证。

### MySQL 全量存储，Redis 做热数据读缓存

Redis 按房间缓存最近的消息。历史查询能被缓存覆盖时读 Redis，否则读 MySQL。缓存可随时从 MySQL 重建。

### 重发用 `client_msg_id` 去重

客户端为每条消息生成 ID，`(room_id, member_id, client_msg_id)` 建唯一约束。重复请求返回原消息的 `seq`，不消耗新序号。

备选方案是 Redis 短期去重，或由用户手动重试。前者在 Redis 切换时会失效，后者服务端最简单，但后续 AI 可能因重复消息被多触发一次。

### 成员模型

房间成员和消息都引用成员，不直接引用用户。成员分 `human` 和 `ai`，第一阶段只创建 `human`。

### 房间采用邀请制

任何房间成员都能按用户名邀请其他用户，邀请单独存放，被邀请者加入后才成为成员。房间列表只返回已加入和待加入的房间。对非成员，房间相关接口一律返回房间不存在，不暴露房间是否存在。

备选方案是公开房间，或者用邀请链接。前者任何用户都能看到房间，后者链接一旦外泄就无法控制谁能进入。

### 最后一名人类成员退出时删除房间

人类用户退出时，失去该房间的读取权限，其消息留给其他成员，聊天记录由用户退出前自行导出到本地。只有人类成员会让房间继续存在，AI 成员不计入。

最后一名人类成员退出时，在同一事务内删除房间、成员、邀请和消息。加入、退出和邀请都先锁住房间行，保证判断“是否最后一名”时结果确定。

事务提交后，通过该房间的 worker 清除 Redis 缓存，排在正在分发的消息之后，避免被它重新写入。这个任务不受队列长度限制。

删除需要请求带上 `confirm_delete`。客户端打开退出对话框后，其他成员可能已经退出，它看到的人数不一定准确，所以由服务端在事务内判断：会删除房间但未确认时，返回 `confirmation_required`，不做任何改动，客户端再提示删除不可恢复。

导出由前端通过历史查询完成，文件保存在用户本地，服务端不另存副本。

备选方案是退出时同时删除该用户的消息，隐私更好，但其他成员的记录和 AI 上下文会缺失，`seq` 空洞还要靠占位记录和删除事件处理。

### 登录态存 Redis，部署一主一从

登录时生成随机令牌，令牌放在 `HttpOnly` Cookie 中，Redis 只存令牌哈希和会话数据，用 TTL 控制过期。Redis 启用密码认证。用户名不含控制字符，否则空字符会让用户名在写入 Redis 时被截断，造成冒充。WebSocket 握手时校验会话和 `Origin`，每次发消息时再校验会话有效且用户是房间成员。

- MySQL 为准加 Redis 缓存：切换时不丢数据，但多一层缓存一致性逻辑。
- JWT：无状态，但过期前难以撤销。

### 容器内构建

用多阶段 Dockerfile 从源码构建固定版本的 Drogon，启用 MySQL 和 Redis 支持。CLion 通过 Docker 工具链在同一镜像内构建和调试，MySQL、Redis 和 Nginx 由 Docker Compose 启动。Drogon 的补丁在 `docker/` 下，镜像构建时应用。

密码放在 `.env` 中，不进 Git，也没有默认值，缺少时 Docker Compose 拒绝启动。仓库提供 `.env.example` 作为模板。

备选方案是本地原生构建，增量编译通常更快，但要维护两套依赖，还要处理本机 Homebrew Drogon 和 Oracle MySQL 客户端库的路径冲突。

## Risks / Trade-offs

- [Redis 主节点故障时，手动切换前会话校验和实时推送中断，此时无法发送消息，也无法访问需要登录的接口] → 第一阶段接受；已保存的消息不受影响，恢复后客户端按 `seq` 补齐；自动切换在多实例阶段实现。
- [主从切换可能丢失最近的会话写入] → 受影响用户重新登录；刚登出的会话可能短暂恢复，第一阶段接受。
- [Drogon 无法感知 Redis 主节点变化] → 多实例阶段选择 HAProxy、应用内监听 Sentinel 或虚拟 IP 之一。
- [单房间写入受行锁和提交延迟限制] → worker 串行排队并设上限；用压测确定实际上限。
- [同一 worker 上的房间相互排队] → worker 数量可配置，按压测结果调整。
- [推送乱序或丢失] → 客户端按 `seq` 排序并补齐。
- [已建立的 WebSocket 连接在会话失效后仍能收消息] → 第一阶段发送时拒绝；断开连接的机制后续再加。
- [房间删除不可恢复] → 前端在每个人类用户退出前提示导出，最后一名退出时额外提示删除不可恢复。
- [消息很多的房间，删除事务可能较慢] → 第一阶段接受；压测后再决定是否分批删除。
- [退出者的发言在房间删除前仍留在服务端] → 第一阶段接受；本次不提供单独删除。
- [房间已删除但 Redis 不可用，缓存清除失败] → 缓存保留到 24 小时过期，期间任何人都读不到，因为历史查询先校验成员身份。
- [`.env.example` 的占位密码也能启动] → 第一阶段接受，由部署者替换。
- [Drogon 补丁随版本升级可能失效] → 补丁应用失败时镜像构建失败；升级前重新确认上游是否已修复。
- [Drogon 源码构建失败或与依赖不兼容] → 第一个里程碑先跑通镜像和 `/health`，验证 MySQL、Redis 连通后再开发业务。

## Migration Plan

这是首次部署，没有存量数据需要迁移。

1. 构建镜像，用 Docker Compose 启动 Nginx、应用、MySQL 和 Redis 一主一从。
2. 通过 `/health` 确认 MySQL 和 Redis 可用。
3. 依次交付账号、房间、实时消息和 Vue 前端。

回滚方式是重新部署上一版镜像。

## Open Questions

- worker 数量、队列长度和 Redis 热缓存的消息条数，用压测结果确定。
- 会话 TTL 和客户端等待补齐的超时时间，按体验调整。
