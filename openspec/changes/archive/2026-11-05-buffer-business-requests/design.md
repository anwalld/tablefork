# Design

## Context

当前两个C++实例只通过redis-proxy访问业务Redis；切换脚本已确认实际IP再清连接，但没有业务闸门。原HTTP控制器、WS发送和服务事务需要复用，不能用重放Redis字节流代替业务命令。前端有界重试已在adcd294完成并归档。

## Goals / Non-Goals

**Goals:** 按docs/request-buffering-plan.md最新决定，所有既有业务入口暂停时转为共享异步任务；真实认证/持久化结果保持。
**Non-Goals:** 不实现持久化任务队列、队列Redis主从、容器停止/断网、全局单一限速或后台真实模型费用测试。WS握手、订阅管理、控制和健康检查作为连接/控制通道单列，不序列化进程指针或连接回调。

## Decisions

- D1：新增命名为queue的Redis连接及单独服务。请求保存为加密业务描述，不保存C++回调。稳定业务request_id与队列task_id分离；客户端领取凭证仅存其哈希/认证值。原子脚本处理入队去重、FIFO领取、45秒过期、等待字节计数和结果所有权。
- D2：HTTP控制器共用入场闸门，捕获框架已绑定的路由名/参数及解析后的认证Cookie；暂停/恢复期202受理，任务执行重新构造可信业务请求，经同一控制器和真实认证。内部执行使用仅进程内可设的request attributes，不通过可伪造HTTP头。注册的路由名/原参数直接分派，避免Unicode、百分号或编码斜线二次解析。WS发送保存会话凭据及消息数据，执行时重新检查会话/成员与用户限流；保留client_msg_id。
- D3：任务状态waiting/running/succeeded/failed/expired/unknown；结果缓存包含原状态码、正文和必要Cookie，加密后保存。查询只凭安全领取证明，匿名登录同样可领取。任务查询不重新触发原业务，不把查询不可用当成执行失败。
- D4：SQL写操作在业务事务中插入请求/结果记录，唯一键约束调用者、操作及请求编号，校验参数指纹。正常与排队共用编号入口。房间、成员管理和AI成员的事务逐接口接入；注册单独绑定匿名提交凭证。聊天复用消息唯一键。Redis会话操作与gRPC key存储单列可恢复性，缺乏安全去重时不自动重放，保留unknown。登录/登出/刷新和key存储在同一请求编号表先提交kind=external的意向标记；重复只返回未知，不重做跨存储副作用，不把凭据放入SQL结果。
- D5：执行许可使用后端本机单调时钟、启动标识、协调代次、修订号及一次性challenge。有效期从challenge发起起算，不从grant送达起算；过期/重放/错启动标识均拒绝。恢复前协调者以有界旧许可期限或确认暂停证明旧执行权失效。新业务入口、任务领取/开始及挂起后新副作用前检查，不能只靠定时器。
- D6：原脚本协调角色不变。受控入口先暂停屏障再Sentinel FAILOVER，缺确认取消。自动故障先维护代理/清旧会话，验证新主/FQDN/实际IP；等待旧许可失效，只给当前握手健康实例恢复许可。控制、查询与存活检查独立于业务桶。
- D7：默认1024条/16MiB请求体，每实例50/s且8并发，结果5分钟/约1秒查询。等待体之外的元数据、执行中载荷和结果缓存计入独立内存预算；Redis noeviction、压力下拒绝受理，不能静默淘汰旧等待任务。应用计量64MiB（密文/结果实际长度＋每任务2KiB），Redis上限128MiB留分配器余量，单结果密文上限16MiB以容纳最大100条历史查询。

## 接口矩阵与结果边界

| 路径/动作 | 受理与执行 | 恢复依据 |
| --- | --- | --- |
| GET /api/* | 暂停入桶，执行前重查身份 | 无写副作用，可按权限重新读取；不能重放副作用接口 |
| 房间/成员/封禁/AI成员写操作 | 暂停入桶，复用控制器及事务 | MySQL请求记录与业务写同事务 |
| 注册 | 匿名凭证绑定、密码载荷加密 | 注册事务与提交编号，不能只按用户名猜请求 |
| 登录/刷新/登出 | 入桶，最终查询交付原Cookie | Redis副作用逐项核实；无证明不盲目接手 |
| API key存储 | 载荷加密，复用现有gRPC | 外部结果不明时unknown，不伪称MySQL事务覆盖 |
| WS send | 保留逻辑消息ID，会话/成员/限流重查 | 已有消息唯一键及保存后ACK |
| WS握手/订阅、健康、内部控制、结果查询 | 连接/控制通道，不走业务等待队列 | 独立认证和可用性处理，不能成为恢复死锁 |

## Risks / Trade-offs

- [内存共享服务重启可丢任务] → 结果未知与业务MySQL记录分开，不能把丢队列当作没执行。
- [MySQL提交与Redis副作用不能成为一个原子事务] → 逐接口恢复/幂等证明；不盲重放，不声称全系统exactly-once。
- [旧控制消息及挂起进程恢复] → 一次性challenge、有界许可、代次校验、实际副作用前检查；用确定性时钟及选择性断链测试证明。
- [排队改变故障窗口响应形态] → 新协议验证首次受理和最终结果，保留原30秒恢复、旧主零连接、权限及持久化要求。

## Migration Plan

新增MySQL请求记录迁移与专用Redis，新增任务密钥和内部控制令牌，由环境提供且不输出。协调能力启用前，后端启动默认暂停等待许可。先在隔离Compose环境运行fake模型和真实故障回归。回滚时先停止受理并处理任务/未知结果，保留业务请求去重记录，不清业务卷。

## 运行与恢复补充

- 实际故障验证发现：Docker动态分配可能在代理重启后复用原IP，而Drogon仅启动时解析Redis域名，可能连到占用旧IP的副本（已观察到READONLY）。Compose为redis-proxy和queue-redis指定固定地址，并将普通容器动态分配池放在这些地址之外。修改DOCKER_SUBNET时必须同时修改动态池和两个固定地址。现有网络迁移需维护窗口重建网络并保留数据卷；不自动部署到原项目。真实重启验收必须记录同容器、同IP，不能靠重启全部后端掩盖。

- 正常直通表示不创建异步任务；仍通过共享状态原子决定直通/排队。因此共享Redis故障时正常新请求也返回可重试503，不能在未知积压状态下旁路。控制、业务健康检查及任务查询独立于业务执行许可。
- 领取到执行完成之前保留原载荷和claim token；可证明安全的SQL/读取任务在领取期限后转recovering，由新实例按原编号重新进入同一事务保护。原执行者的旧claim不能写回。会话/gRPC任务则进入unknown。
- GuardedTransaction随协程携带许可，不使用thread_local；每个SQL发送和commit前重查。未显式take提交的包装析构会rollback，避免异常时Drogon自动提交部分写入。GuardedRedis对每次请求副作用重查原stamp。
- 现有watcher按功能开关调用同目录Python标准库协调模块；仍只操控原HAProxy和Sentinel。续约线程发送grant时持phase锁，revoke取得该锁后不会再发送旧phase的grant；延迟challenge回复必须再次匹配phase。旧grant的challenge已在revoke前产生，等待原始TTL后失效。单个现有代理协调者重启先建立新epoch并等旧TTL，不复用旧进程许可。
- SQL请求记录不随房间删除清理，首版不自动过期；后续维护必须保留拒绝旧编号的证明。加密/参数HMAC密钥是稳定部署秘密，不能在仍有待执行/恢复请求时随意更换。

## PR #12 double check 修正（2026-11-06）

- HTTP排队结果未知不能伪装成退出成功。App仅在真实logout成功后清用户；等待期间只允许一个logout，unknown/queue_timeout保留当前聊天和明确提示。房间、成员、审批、API key界面共用明确的未知/超时文案；key删除未知不清元数据或发成功通知。
- 持久化ACK后的消息分发可能晚于房间删除，且可能发生在另一实例。本地room worker串行不足以保护共享缓存。分发在SQL只读事务中以`SELECT ... FOR SHARE`锁定仍存在的房间，持锁完成缓存写；删房的独占锁等待既有写者，删房提交后新分发看不到行。持锁阶段后释放只读事务，再发布消息，不把ACK改为缓存持久化确认。
- 删房控制器等待Redis DEL完成再报告成功。SQL已提交而清理失败/许可过期返回503/result_unknown、retryable=false，不宣称SQL回滚；复用原请求编号时，SQL结果对账先完成当前已删除房间的缓存清理再通知。跨MySQL/Redis仍不是全局原子事务。
- CI恢复探针最多保留一个登录在途，避免同账号堆积触发合法429。默认限流未放宽，真实12次排队错密码登录验证5次401、7次429且retry_after为正。原5秒首次响应、30秒恢复、0.3秒删缓存断言保持。
