# Design

## Context

见 proposal。当前实际零发送也会累计 attempts；20 秒即失败。单纯把自增移到 write 后仍不能覆盖连接保持打开但 Redis 返回暂时性错误的窗口，因此使用统一的时间预算。

## Goals / Non-Goals

**Goals:** 保留现有内存 outbox、原 ID 去重和 ACK 含义，以有限等待覆盖 30 秒恢复及重连退避。

**Non-Goals:** 不实现后端暂停协议、临时队列、刷新后恢复或新 UI；不修改服务端恢复/认证/限流标准。

## Decisions

- D1：每条消息从 send 时起算 60 秒，记录绝对 expiresAt 与独立 deadlineTimer。替代四次即失败；重连、限流或暂时性错误均不重置期限。60 秒覆盖 30 秒恢复和最多 10 秒的连接退避，仍提供明确失败出口。
- D2：write 真正返回成功后才增加 attempts、启动原 5 秒 ACK 等待。离线时由连接恢复事件继续发送，独立期限仍可终止离线等待。暂时性错误使用按已发送次数递增、最多 5 秒的退避。
- D3：服务端限流设置 notBefore，重连也检查此时间；期限到达优先结束，不让长 retry_after 无限延长等待。
- D4：settle 同时清理两类定时器；主动关闭和 4401 共用停止清理，取消重连并清空 pending。发送前检查条目仍有效、客户端未关闭和绝对期限，防止后台页面延迟执行或迟到事件重发。

## Risks / Trade-offs

- [期限内实际重发次数可能超过原四次] → ACK 等待与递增退避限制频率，原 ID 去重、服务端限流保持不变。
- [页面冻结使浏览器定时器延后] → 恢复发送前再次核对绝对期限；不承诺页面关闭后恢复消息。
- [服务器已保存但 ACK 丢失] → 原 ID 重试；客户端测试验证发送 ID 不变，不冒称浏览器单测证明数据库只保存一条。

## Migration Plan

前端构建部署即可，无数据库迁移或依赖变化。回滚恢复 ChatSocket 与对应测试；现有协议不变。
