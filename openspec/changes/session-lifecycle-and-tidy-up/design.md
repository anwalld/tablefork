# Design

## Context

动机见 proposal.md，要求见 `specs/realtime-messaging` 和 `specs/user-auth`。

和本设计有关的现状：

- 会话存在 Redis：键为 `session:<sha256(令牌)>`，`SET ... EX`，默认 7 天（`SESSION_TTL_SECONDS`）；会话 Cookie 的 `Max-Age` 也是 7 天。
- `ChatSocket` 在连接建立时把会话和令牌存进连接的上下文，每次发消息都重新读一次会话；除此之外不再检查会话。
- `RoomHub` 只记录订阅了房间的连接，没订阅任何房间的连接不在任何表里。
- 设备 Cookie 是 `Path=/api/auth`，只有认证接口能收到；`device:<sha256(令牌)>` 对应用户名。每次登录成功，浏览器都会拿到设备令牌（上一阶段为登录延迟设计）。
- 已有的 Redis 订阅器（`RoomHub::subscriber()`）用于房间频道。
- Drogon 的 `setPingMessage` 只负责 WebSocket 层的保活 ping。

## Goals / Non-Goals

**Goals:**

- 登出后立即断开、过期后有界延迟断开，并且在多实例下成立。
- 检查的开销与连接数成线性关系，每个检查周期最多几次 Redis 往返。
- 续期不改变会话令牌，已建立的连接不需要重连。
- 每个用户受信任的设备有上限（一台手机、一台电脑），替换规则可预测。

**Non-Goals:**

- 管理“我的所有会话”、远程登出指定设备、手动指定受信任设备。
- 改变会话的默认时长。

## Decisions

### D1 连接注册表与自己的检查定时器

新增 `SessionWatcher`（每个实例一个）：

```text
连接建立  -> 记录 连接 -> 会话键（session:<hash>）
连接关闭  -> 删除记录
定时器    -> 每 SESSION_CHECK_SECONDS（默认 30）秒：
             取出所有不同的会话键，按每批 500 个用 MGET 查询
             值为空 -> 会话已结束 -> 断开使用它的所有连接
             Redis 出错 -> 本轮不处理，记日志
```

- 定时器用 Drogon 主事件循环的 `runEvery`，与 `setPingMessage` 无关。保活 ping 保持不变。
- 为什么不用每个连接一个定时器：一个实例可能有上万个连接，合并成一次批量查询更省。同一个会话的多个标签页也只查一次。
- 为什么 Redis 出错时不断开：一次 Redis 抖动不应让所有用户同时掉线。这和限流时“出错就拒绝”不同，那里放行有安全风险，这里不断开只是推迟了下线。

### D2 登出立即断开（跨实例）

- 按用户的会话索引：创建会话时把会话键加入集合 `user_sessions:{user_id}`（集合的过期时间随会话续期一起延长）。集合里可能残留已过期的会话键，使用时忽略即可。
- 登出时按 D7 判断：会话所在设备是受信任设备 -> 结束该用户的所有会话（删除集合里的全部会话键和集合本身）；否则只删除当前会话，并从集合中移除。
- 每个被删除的会话键都向 Redis 频道 `sessions:ended` 发布一次。
- 每个实例的 `SessionWatcher` 订阅这个频道，收到后立即断开本实例上使用该会话的连接。
- 即使广播丢失（Redis 短暂不可用），定时检查也会在一个周期内补上。

### D3 断开方式

- 关闭码 `4401`，原因 `session_ended`。用应用自定义的 4xxx 区间，前端能和网络断开区分开。
- 断开前先从 `RoomHub` 里移除这个连接，避免断开过程中还有推送发出。
- 前端 `ChatSocket` 的 `onclose` 收到 `4401` 时，设置 `closed`、不再重连，并通知视图回到登录页（等同于登出后的状态）。

### D4 续期接口

```text
POST /api/auth/refresh
  1. SessionStore::require(req)                    -> 无效则 401 unauthenticated
  2. DeviceTrust::evaluate(会话的设备)              -> 先按 D7 重新判断一次
  3. 会话的设备不受信任                              -> 403 device_required
  4. EXPIRE session:<hash> SESSION_TTL_SECONDS      -> 返回 0（刚好过期）则 401
  5. 重新下发会话 Cookie（同一令牌，Max-Age 重新计算）；若带着设备 Cookie，设备令牌也续期
  返回 {"expires_in": SESSION_TTL_SECONDS}
```

- 只延长已经存在的会话，所以登出（会话已删除）之后无法通过续期“复活”会话。
- 前端：登录成功或页面加载确认已登录后，每 6 小时调用一次；失败不提示用户，403 时停止定时调用。会话 7 天，6 小时的间隔足以让每天打开的受信任设备一直保持登录。
- 续期接口在 Nginx 的认证限流范围之外（只匹配 `login|register`），不受每分钟 10 次的限制。

### D5 测试数据清理脚本

`tests/integration/cleanup_test_data.py`，在测试容器里运行（已有 `pymysql` 和 `redis`）：

```text
docker compose --profile test run --rm tests python cleanup_test_data.py [--apply] [--prefix owner_ ...]
```

- 默认匹配集成测试生成的用户名：`^u[0-9a-f]{12}$`，以及“按字符计数”测试生成的 `^用户u[0-9a-f]{5}$`；`--prefix` 追加前缀匹配；`--exclude` 排除用户名（默认排除 `realtest_` 开头的账号）；`--only-prefixes` 跳过默认规则，只按前缀匹配（脚本自己的测试用它，避免误删并发运行的其他测试的数据）。
- 开始时显式开启事务：即使调用方的连接开着自动提交，预演也一定会回滚。
- 在一个事务里，按外键顺序：
  1. 成员全是待删用户（以及 AI）的房间：整间删除，消息、成员关系、邀请和 AI 申请级联删除。
  2. 其余房间里：删除待删成员发的消息、成员关系、待删用户收到的邀请、待删成员提交的 AI 申请。
  3. 待删用户是其余某个房间的群主时，把群主转给该房间最早加入的其余人类成员。
  4. 删除待删成员和用户（API key 级联删除）。
- 提交后清理 Redis：被删房间和“删过消息的共享房间”的热缓存（否则历史查询会从缓存里读到已删的消息）、被删房间的 AI 状态和计时器（`ai:room:{id}`、`ai:timers`、`ai:work`）、被删用户的受信任表和会话索引（`trusted:{id}`、`user_sessions:{id}`）。会话键本身让它们自然过期。
- 不带 `--apply` 时只打印每一步的数量，然后回滚。

### D6 小的遗留

- `keys.py`：`INSERT ... VALUES (...) AS new ON DUPLICATE KEY UPDATE ciphertext = new.ciphertext, ...`（MySQL 8.0.19 起支持）。
- CI：`actions/checkout@v5`。

### D7 受信任设备

```text
设备          = 设备令牌的 SHA-256（登录时已有令牌就沿用，没有就新发）
设备类型       = 按登录请求的 User-Agent：含 Mobile/Android/iPhone/iPad/iPod/Tablet -> phone，否则 computer
会话          = 记录 user_id、member_id、设备、设备类型、用户名（新格式带 v2 前缀，旧格式会话仍可读，视为没有设备）
受信任表       = trusted:{user_id}  哈希：phone -> 设备、computer -> 设备
发送计数       = device_sends:{设备}:{YYYYMMDD}  每天一个计数，保留 31 天
```

- 每条人类消息保存成功后，按会话里的设备给当天的计数加一（失败只记日志，不影响发消息）。
- 判断（登录成功后、续期时，用 Lua 原子执行，避免两台设备同时登录互相覆盖）：

```text
该类型没有受信任设备            -> 这台设备成为受信任设备
受信任设备就是这台               -> 不变
否则 读两台设备最近 30 天的计数和   -> 新 > 1.5 × 旧 时替换，否则不变
```

- 登出时：会话的设备 == 受信任表中该类型的设备 -> 结束全部会话；否则只结束当前会话。
- 登录延迟的设备豁免（上一阶段）不变：任何登录过的设备都有自己的失败计数，与是否受信任无关。
- Lua 脚本在脚本内部拼接 `device_sends:*` 键名，不兼容 Redis Cluster；当前是单主 Redis，换成 Cluster 时要改为由调用方传入全部键。
- 为什么把设备记进会话：WebSocket 收不到设备 Cookie（它只在 `/api/auth` 下发送），发消息时只能从会话里找到设备。这样设备 Cookie 的作用范围不用扩大。

## Risks / Trade-offs

- [过期后最多晚 30 秒断开] -> 规格允许“在检查间隔内”；间隔可配置，调小会增加 Redis 查询次数。
- [Redis 不可用时已过期的会话还能多收一会儿消息] -> 有意为之，见 D1；Redis 恢复后的下一个周期就会断开。
- [续期让常用设备长期保持登录] -> 只在受信任设备上生效，每类最多一台；长期不打开的设备会话照常过期。
- [User-Agent 可以伪造] -> 伪造最多让一台设备被归到另一类，换不来别人的令牌或会话；后果只是受信任设备的归类不准。
- [发送计数可以刷] -> 刷消息受消息限流约束（每 10 秒 30 条），且只能让自己的设备变成受信任设备，不影响别的用户。
- [清理脚本误删真实数据] -> 默认只预演；匹配规则保守；排除列表默认包含 `realtest_`；单事务，出错整体回滚。
- [4401 关闭码与浏览器或代理的行为] -> 4000–4999 由应用自定义，Nginx 会原样转发；集成测试直接检查关闭码。

## Migration Plan

无数据迁移。部署后，已有会话是旧格式（没有设备信息），视为来自非受信任设备：登出只结束当前会话、不能续期；用户下次登录后即按新规则判断。旧版前端不认识 4401，会尝试重连，但重连会因为会话无效被拒绝，刷新页面后即回到登录页。
