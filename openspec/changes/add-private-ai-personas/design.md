# Design

## Context

基线PR #13：`ai_profiles(member_id,slug UNIQUE,provider)`只有四个公共AI；`members.display_name`保存名字，模型和默认人设在`ai/agents.toml`。`AiService`、Python规则及Redis状态依赖slug，gRPC没有房间人设或入群代次。PR #13新增`ai_generations`持久控制快照、停止/暂停、结构化提及及共享桶业务分派。

阶段一已完成正式OpenSpec和数据库结构并停止汇报，见phase-1-report.md。用户随后授权继续完整apply、verify与交接；以下完整目标现在纳入实施，不自动归档、部署或合并。

## Goals / Non-Goals

**Goals:** 将模型类型、私人角色、房间配置拆开；保留旧成员/消息；为角色隔离、人设固定版本、退出代次隔离和原控制机制提供数据基础。

**Non-Goals:** 不升级原服务、不发送真实模型请求。阶段一只交付结构的限制已由用户追加授权解除。完整change不包含公共角色市场、角色转让、全局默认人设编辑、用户删除账户或角色删除/改名功能。

## Decisions

### 1. 复用成员ID作为角色ID，分离模型类型

新增`ai_model_types`，四行`model_slug/display_name/provider`，slug仍为`deepseek/gpt/claude/gemini`；具体API模型名称继续由现有部署配置管理，不复制进每个角色。

扩展`ai_profiles`：`model_slug`指向模型类型，`creator_user_id`指向创建者账户，`is_legacy`标识旧公共成员。`member_id`既是稳定角色ID也是聊天成员ID，名字继续保存在`members.display_name`。不再发明一个与成员ID重复、容易串联的角色ID。

旧`slug`及其唯一索引暂保留，作为兼容旧程序和旧快照的技术标识；后续新私人角色由服务端生成`role_<member_id>`，不允许用户指定，不用它判定模型类型。新接口用成员ID，`model_slug=claude`的多个角色不会冲突。后续启动校验比对四类模型而不是要求角色集合恰好等于四个TOML项。

约束：模型slug与provider使用组合外键保证匹配；旧角色创建者为空且旧slug等于模型slug，私人角色创建者非空且技术slug与模型slug不同。创建者外键不级联删除角色，避免历史成员被删除。

备选：给每个角色复制完整模型配置会造成模型升级和key归属混乱；另建角色表并长期并行ai_profiles会制造两份身份源。因此采用扩展原表并保留兼容字段。

### 2. 房间人设与入群编号

新增`room_ai_personas`：主键`(room_id,member_id)`，保存`admission_id BINARY(16)`、`persona TEXT`和`persona_version BIGINT UNSIGNED`。入群编号全表唯一且为非零16字节；新入群由后端生成安全随机值。版本从1开始，每次提交编辑递增，同一入群内以`WHERE persona_version=?`实现乐观并发检查。人设限制UTF-8编码后不超过16KiB，空人设合法。

组合外键指向`room_members`并随AI离房级联删除，另指向`ai_profiles`防止为普通人类创建AI配置。重新入群新建配置并生成新编号，即使版本重新从1开始，也不会与旧入群相混。

旧已入群AI回填配置行及唯一入群编号，人设留空，仍由旧生成路径使用原TOML默认人设；本阶段不把部署配置硬编码进SQL，不改变旧AI行为。完整功能中旧角色也沿用原默认人设，界面只读标记旧版。

备选：只用房间与成员ID不能区分离房前后；只用版本号在删除重建后可能相同，因此同时保存独立入群编号。

### 3. 申请与生成快照

`ai_member_requests`增加`persona TEXT NULL`；旧申请保持NULL和原记录，私人角色API将要求写入显式字符串（包括空串）。批准直接复制已申请人设，不允许审批者改写；创建者退群同事务清理，旧预置待审批可拒绝但不可在完整功能启用后批准。

`ai_generations`增加可空`admission_id/persona_version/persona_snapshot`及按房间/成员/入群/状态索引。三个字段必须全空（升级前/旧路径）或全有效（新协议），避免半份快照；版本大于0且正文不超16KiB。不对当前房间人设建外键：AI离房会删配置，但旧生成的控制/去重记录必须保留，后续服务端用当前关系重新验证入群编号，而不是让外键删除生成记录。

新一轮开始才读取并在SQL持久登记人设，之后同generation_id恢复只读该快照。第一次开始前崩溃重试可读更新后人设；SQL登记成功后崩溃，则以已登记快照为准。Redis任务也带相同成员ID/入群编号/版本；SQL与Redis不一致时以SQL固定版本恢复，不用最新配置覆盖已有逻辑回复。Chunk/Final/Failed添加新字段时使用新的protobuf编号，旧字段不复用；完整切换后私人角色缺少入群编号的动作必须被拒绝。

### 4. 权限、API与现有基础能力

拟新增`GET /api/ai/models`及`GET/POST /api/ai/roles`；后者只列/建自己的角色。房间邀请与审批改用具体成员ID，邀请体带persona；房间人设采用`PUT /api/rooms/{room}/ais/{member}/persona`，请求带预期版本。现有旧slug路由完整启用后仅保留必要兼容读取/移除，新增旧AI邀请明确拒绝。具体响应沿用项目错误结构；邀请及移除房间外他人角色时，越权私人ID与不存在ID都返回`ai_not_found`。

所有写入口加入可信共享桶分派和SQL同事务请求记录，重放复用原编号与结果；执行时复查创建者和成员关系。采用既有memo→room锁序；角色创建在同一事务写members、ai_profiles和业务结果，不因结果查询重试产生第二角色。人设编辑同事务检查版本、存更新和回执。

创建者退出/踢出/封禁与审批锁同一room，查询其角色并删除room_members及相关请求；随后发布取消/成员事件。广播片段与保存Final均验证当前入群编号，旧动作不能仅凭generation_id或member_id过关。移出不等同于人工停止：未在离房前成为正式历史的旧生成不得在离房后补存部分文本；PR #13正常停止保存部分内容的行为继续保留。

模型输入按系统身份规则、房间人设、近期房间历史组成；系统元数据提供角色名、模型及创建者，人设文本是内容配置，不是权限或付款依据。payer继续来自原触发者，接话/冷场不得换成创建者。

### 5. 提及与前端

复用PR #13的成员补全和结构化提及，候选增加创建者及模型；选中保存真实member_id。旧文本仅在当前房间名称唯一时识别，歧义不随机选也不全触发。Python对话对象/任务从模型slug切到具体成员及入群编号，模型只用于选择适配器。

“我的AI”负责选择模型与名字创建；邀请窗口填写本房间人设；只有仍在房间的创建者可编辑，管理者不能越权编辑。旧版显示标签与历史成员身份分开，不批量改写旧消息名字。

## Risks / Trade-offs

- [兼容字段有冗余] → 目前保留slug/provider以兼容PR #13；组合外键防模型/provider错配，新写入必须明确新字段。
- [数据库不能单独证明所有权/当前在房间] → FK和CHECK只保证结构，后续服务事务鉴权及动作入群校验仍必需，不能宣称V7已经实现权限隔离。
- [旧程序会看到新私人角色而启动校验失败] → 启动校验已改查四类模型表，仍需C++/Python/前端同批升级，不能用旧应用直接读取私人角色库。
- [MySQL DDL隐式提交，失败不能整体回滚] → 在一次性空库及含V6数据的升级库真实跑Flyway并保留失败日志；原库部署需另获授权，事先备份。
- [入群编号不是授权凭证] → 仅用于代次隔离，身份与房间权限仍独立校验。
- [DB快照正文增加空间] → 16KiB字节上限；按现有生成状态生命周期处理，日志不输出人设正文或key。

## Migration Plan

1. 本阶段新增V7，不修改V1—V6或主规格；创建模型目录，回填旧profiles的模型类型/旧版标志，保留成员ID、名字、历史、旧申请及旧生成控制字段。回填已有AI房间配置；旧生成三项快照保持NULL以兼容PR #13。
2. 用一次性MySQL 8.4.6/Flyway 11.14.1验证新库及V6升级，Flyway重复migrate无重复数据且validate通过；检查多角色同模型、创建者约束、provider错配、房间隔离、退群配置删除/历史与生成保留、快照完整性与16KiB边界。旧版SQL写入形状仍可用。
3. AI账号仅新增模型目录和房间人设SELECT权限，沿用原生成控制权限；仍禁止读用户表和人类成员的user_id，对允许和拒绝范围进行验证。
4. 后续完成功能与专项/完整回归后，再统一升级C++/Python/前端，启用私人邀请并禁止旧角色新邀请。归档前对照全部任务verify；只完成前两项时保持change活动。
5. 本轮不部署。未来部署失败优先回退应用并保留兼容新增列；产生私人角色后不得直接降回只认四个AI的旧版本。移除表/列的破坏性回退需要单独的数据迁移方案和授权。
