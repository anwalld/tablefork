# Proposal

## Why

AI最终失败目前会清空内容并复用成功保存状态，用户无法在历史中辨认失败。停止控制存在高频数据库读取，消息搜索依赖逐条子串扫描，Redis断连修复也需要持续回归验证。本变更统一改善生成结果表达、控制效率、搜索性能与聊天室故障恢复。

## What Changes

- 将生成处理阶段与结束结果分开表达，区分成功、失败、人工停止和取消，整理现有`status`与`stopped`的重复含义。
- 已开始的逻辑生成最终失败时，保留最近一次有文字的尝试的部分文本并标注失败；没有文本也生成一条失败历史记录。失败内容在刷新后可见，模型上下文跳过失败消息，失败不引出AI接话或置位主动发言成功标记。
- 沿用同一`generation_id`和递增尝试编号，重试替换本次草稿，最终只形成一条逻辑回复。缺少key等生成前置拒绝继续采用提示事件。
- 通过现有gRPC链路传递SQL提交后的控制变更提示，配合可配置的低频SQL校验与重连同步，减少Python及C++重复读取停止状态的次数。
- 评估MySQL原生ngram全文索引作为搜索候选过滤，再以既有字面子串条件复核；短词、特殊字符及无法保证召回的情况采用准确的回退查询。
- 增加Redis断连后发送、回调完成、重连和故障窗口的回归，核查补丁及原登录超时、堆损坏之间的关联，记录可复现的机制与版本适用条件。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `ai-replies`：最终失败的持久历史、空失败记录、上下文排除、失败结果确认与重投。
- `ai-controls`：统一控制结束原因，提交后控制通知、低频校验、通知丢失与恢复时的可靠停止。
- `message-search`：索引候选与准确回退，保留权限、字面子串、排序和分页语义。

Redis部分强化现有`high-availability`行为的实现和验证，复用既有故障恢复要求。

## Impact

- MySQL新增迁移，涉及`ai_generations`、消息结果元数据和搜索索引；旧迁移保持校验可重复执行。
- C++生成结果保存、控制接口、流式事件、历史与搜索查询；Python生成恢复、上下文和控制检查；gRPC事件与结果字段；Vue失败消息展示。
- Redis补丁适用性、依赖库内存诊断、故障编排和已有结构化日志。
- **BREAKING** 内部生成状态表示需要迁移，旧Redis任务、消息与生成记录需要兼容读取或转换，C++、Python与前端需协调升级。

## 设计更改对照表

| 原来 | 提案 | 确认程度 |
| --- | --- | --- |
| 最终失败写成saved并清空内容 | 记录明确失败结果，保留部分文本 | 已确认产品行为 |
| 失败后移除草稿 | 失败内容进入历史，刷新可见并带失败标记 | 已确认产品行为 |
| 零输出失败仅发送提示 | 历史保留一条“生成失败”记录 | 已确认产品行为 |
| 没有可供模型读取的失败历史 | 展示失败历史，模型上下文跳过失败消息 | 已确认产品行为 |
| status混合阶段与结果，另有stopped | 分离处理阶段与结束结果，兼容派生原停止标记 | 设计建议 |
| 每100ms及每片段重复读取停止状态 | 控制通知唤醒，低频SQL校验与恢复同步 | 设计建议 |
| LOCATE扫描全部候选 | 索引缩小候选后准确复核，不能保证召回时回退 | 设计建议 |
| 断连补丁主要依赖既有CI验证 | 固定版本回归、内存诊断和有界故障窗口取证 | 设计建议 |

## 验收边界

失败、停止、完整结果和成员移出并发时只能形成一个合法终态；保存确认和任务结果必须可恢复、可去重。停止通知丢失后仍能从SQL恢复控制状态。搜索优化与原查询逐项比对结果和分页，并给出相同数据和负载下的查询计划及耗时对比。Redis验证保持既有5秒初始响应、30秒恢复、持久化ACK、旧主零连接和权限检查要求。

## 待审阅的建议

- 低频控制校验初值建议1秒并可配置，实际控制完成期限同时考虑数据库调用超时与取消确认。
- ngram索引的适用词形、索引参数和默认启用范围由等价性及性能验证确定。
