# Proposal

## Why

第一阶段只有人类成员，产品的核心——房间里和多个 AI 一起聊天——还没有。数据模型已经为 AI 留好了位置（`members.type = 'ai'`，消息不区分发送者类型），这一阶段把 AI 真正接进来：能被邀请进房间，按规则说话，流式输出，并接入 DeepSeek、GPT、Claude、Gemini 四家模型。调用费用由用户自己的 API key 承担，平台不付费。

## What Changes

- **群主和管理员**：创建房间的人成为群主，群主可以任命和撤销管理员。群主必须先手动转让群主才能退出（是最后一名人类时除外）。已有房间在迁移时，由最早加入的人类成员成为群主。
- **预置 AI 成员**：系统预置 DeepSeek、GPT、Claude、Gemini 四个 AI 成员。任何房间成员都可以申请邀请 AI，但申请人必须已填写该 AI 所属服务商的 API key。群主或管理员邀请时 AI 立即加入，其他成员的申请要由群主或管理员审批。只有群主和管理员能把 AI 移出房间。
- **用户 API key**：用户按服务商（DeepSeek、OpenAI、Anthropic、Gemini）填写自己的 key。保存前先验证，加密存储，之后只显示末 4 位，可以删除或替换。
- **谁触发谁付费**：AI 的每次调用使用触发者的 key——发出 @ 的人、一人房间里的那个人，或接话链起点的人。
- **触发规则**：
  - 只有 1 个人类成员的房间：人发的每条消息都由“当前对话对象”回复（B）；冷场时 AI 主动发言（D）。
  - 2 个以上人类成员的房间：只有被 @ 的 AI 回复（A）。
  - AI 之间可以接话，接话概率按跳数指数衰减，人发消息后重置。
- **对话**：一人房间里，没有对话时随机选一个 AI 并锁定为对话对象；人 @ 某个 AI 就换成它。冷场时主动发言最多 3 条，概率按已发条数衰减，第 3 条是告别，发完对话结束。结束后人再发消息就重新随机选；@ 原来的 AI 可以接着聊。
- **流式输出**：生成过程中，房间里的人能看到 AI 逐段输出（不落库）；生成结束后保存为一条正常消息，分配 `seq`。同一个房间同一时刻只生成一条回复，生成期间人新发的消息合并后再回复一次。
- **出错和缺 key**：模型出错、超时或触发者没有对应的 key 时，不保存任何消息，只给触发者发提示；不自动重试。
- **新的 Python AI 服务**：负责触发规则、对话状态、冷场计时器、模型调用和 key 的加解密。状态都放在 Redis，进程本身无状态。它使用单独的 MySQL 账号 `ai`，只能访问它需要的几张表和列。用策略工厂接入三种接口：OpenAI 兼容（GPT、DeepSeek）、Anthropic、Gemini。
- **C++ 与 Python 之间用 gRPC 双向流**：C++ 把房间事件发给 Python，Python 把流式片段、最终消息和主动发言发回 C++。事件带编号并由 Python 确认，断线重连后重发未确认的事件。最终消息仍由 C++ 的消息服务保存，`seq` 的分配只有一份实现。
- **前端**：API key 设置页、申请和审批 AI 邀请、群主转让和管理员任命、@ 提示、AI 逐段输出的显示、只给自己看的提示。
- **BREAKING**：
  - `chat-rooms` 的“成员类型”要求从“只创建 `human` 成员”改为允许预置的 AI 成员，接口返回的成员信息增加角色和 AI 的标识，旧字段不变。
  - 群主不能再直接退出房间，要先转让群主（是最后一名人类时除外）。

不在本次范围内：用户自建 AI、长期记忆、多人房间里 AI 自己判断要不要插话、平台付费和额度、内容审核。

## Capabilities

### New Capabilities

- `ai-members`：预置 AI 成员的目录，申请邀请 AI（含 key 检查）、群主和管理员审批、移出 AI。
- `ai-replies`：AI 什么时候说话、由谁说、用谁的 key；对话锁定与结束；主动发言；接话衰减；流式输出、合并生成、出错提示。
- `api-keys`：用户按服务商管理自己的 API key：验证、加密存储、掩码显示、删除。

### Modified Capabilities

- `chat-rooms`：“通用成员类型”改为允许 AI 成员并返回角色；“退出房间”增加群主必须先转让的限制；新增“群主”“管理员”“已有房间的群主”三项要求。

## Impact

- **新服务**：`ai/`（Python 3.12、`grpcio`、各家官方 SDK、`redis`、MySQL 驱动、`cryptography`），独立的容器，只在内部网络上开放 gRPC 端口。
- **C++**：Dockerfile 的依赖阶段加装 `libgrpc++-dev` 和 `protobuf-compiler-grpc`；新增 gRPC 客户端和到 Drogon 事件循环的桥接；`MessageService` 增加 AI 消息的保存入口；`RoomHub` 支持只发给某个成员的事件；新增角色管理、AI 邀请与审批、API key 接口（key 只转发给 Python，不保存、不记录明文）；退出房间增加群主检查。
- **接口定义**：新增 `proto/ai.proto`，C++ 和 Python 共用。
- **数据库**：Flyway `V3` 给 `room_members` 加上角色列并为已有房间指定群主；新增 `ai_profiles`（预置 AI 的服务商）、`ai_member_requests`（待审批的 AI 邀请）和 `user_api_keys`（加密后的 key），并写入 4 个预置 AI 成员。另加一个一次性的 `db-users` 服务，用 root 创建并授权 `ai` 账号。
- **配置**：`.env` 新增 key 加密主密钥、gRPC 共享令牌、触发概率和计时参数；主密钥只给 AI 服务。
- **前端**：`ChatView.vue`、新的设置页、`chat-socket.js` 新增 `ai_chunk`、`ai_error`、`ai_notice` 事件。
- **测试**：Python 单元测试（规则、衰减、适配器、加密）；集成测试使用一个“假模型”适配器和假的 key，不调用真实服务商，CI 不需要真实 key。
