# user-auth Specification

## Purpose

让用户通过用户名和密码注册并登录，并为 HTTP 和 WebSocket 接口提供统一的登录态校验。

## Requirements

### Requirement: 用户注册
系统 SHALL 允许访客使用唯一的用户名和密码注册账号。用户名 MUST 为 3 到 32 个字符且不含控制字符，密码 MUST 不少于 10 个字符，MUST NOT 出现在常见密码黑名单中，且 MUST NOT 与用户名相同（不区分大小写）。

#### Scenario: 注册成功
- **WHEN** 访客提交未被占用且格式合法的用户名和密码
- **THEN** 系统创建账号并返回成功

#### Scenario: 用户名已被占用
- **WHEN** 访客提交已存在的用户名
- **THEN** 系统拒绝注册并返回用户名已被占用的错误

#### Scenario: 格式不合法
- **WHEN** 访客提交长度不符合要求的用户名或密码，或用户名包含控制字符
- **THEN** 系统拒绝注册并返回参数错误

#### Scenario: 常见密码
- **WHEN** 访客提交的密码出现在常见密码黑名单中，例如 `password123`
- **THEN** 系统拒绝注册并返回弱密码错误

#### Scenario: 密码与用户名相同
- **WHEN** 访客提交的密码与用户名相同，大小写不同也算
- **THEN** 系统拒绝注册并返回弱密码错误

#### Scenario: 确认密码
- **WHEN** 访客注册时两次输入的密码不一致
- **THEN** 系统拒绝注册并返回两次密码不一致的错误

#### Scenario: 已有账号不受影响
- **WHEN** 规则收紧前注册、密码为 8 到 9 位的用户登录
- **THEN** 系统按正常流程校验密码并允许登录

### Requirement: 密码安全存储
系统 MUST NOT 保存或在任何响应中返回明文密码，只保存加盐的单向哈希。

#### Scenario: 查询账号数据
- **WHEN** 账号注册成功后检查其存储数据
- **THEN** 存储中不存在明文密码

### Requirement: 安全问题找回密码
系统 SHALL 允许忘记密码的用户通过注册时设置的安全问题找回账号。用户提供用户名后，系统 SHALL 返回其安全问题；用户正确回答后 MUST 能设置新密码，答案错误或用户名不存在时系统 MUST 返回相同的错误，不透露账号或答案。安全答案 MUST 以加盐的单向哈希存储，任何响应 MUST NOT 返回答案。重置成功后 MUST 使该用户所有会话失效。

#### Scenario: 找回密码成功
- **WHEN** 忘记密码的用户输入用户名，答对安全问题，并提交符合规则的新密码
- **THEN** 系统更新密码，用户可用新密码登录，该用户此前所有会话失效

#### Scenario: 答案错误或用户名不存在
- **WHEN** 用户提交的答案与所设不符，或用户名不存在
- **THEN** 系统返回相同错误，不透露账号是否存在或答案是否正确

#### Scenario: 未设置安全问题
- **WHEN** 未设置安全问题的账号请求找回密码
- **THEN** 系统返回空问题，用户无法通过安全问题找回

#### Scenario: 答案以哈希存储
- **WHEN** 检查注册设置了安全问题的账号存储数据
- **THEN** 存储中不存在明文答案，只保存其哈希

### Requirement: 用户登录
系统 SHALL 在用户名和密码正确时建立会话，并通过 `HttpOnly` Cookie 下发随机会话令牌。

#### Scenario: 登录成功
- **WHEN** 用户提交正确的用户名和密码
- **THEN** 系统建立会话并在响应中设置 `HttpOnly` Cookie

#### Scenario: 凭据错误
- **WHEN** 用户提交不存在的用户名或错误的密码
- **THEN** 系统返回同样的认证失败错误，不透露用户名是否存在

### Requirement: 登录态校验
系统 SHALL 拒绝未携带有效会话的受保护 HTTP 请求和 WebSocket 连接。

#### Scenario: 会话有效
- **WHEN** 用户携带有效会话访问受保护的 HTTP 接口
- **THEN** 系统正常处理请求

#### Scenario: 缺少或无效会话
- **WHEN** 请求未携带会话，或携带的会话无效
- **THEN** 系统返回未认证错误

#### Scenario: 会话过期
- **WHEN** 用户携带已过期的会话访问受保护接口
- **THEN** 系统返回未认证错误

### Requirement: 用户登出
系统 SHALL 允许已登录用户登出，登出后其当前会话立即失效。当前会话所在的设备是该用户的受信任设备时，系统 MUST 同时使该用户的所有会话失效；否则 MUST 只使当前会话失效，其他会话保持有效。

#### Scenario: 登出成功
- **WHEN** 已登录用户请求登出
- **THEN** 系统使当前会话失效，之后使用该会话的请求返回未认证错误

#### Scenario: 从非受信任设备登出
- **WHEN** 用户在受信任的手机和另一台不受信任的手机上各自登录，从不受信任的那台登出
- **THEN** 受信任手机的会话仍然有效

#### Scenario: 从受信任设备登出
- **WHEN** 用户在受信任的电脑和其他设备上各自登录，从受信任的电脑登出
- **THEN** 该用户所有设备的会话都失效，之后使用任一会话的请求返回未认证错误

### Requirement: 登录失败延迟
系统 SHALL 按用户名统计连续登录失败次数，与请求来源 IP 无关。失败次数超过免费次数后，系统 MUST 拒绝等待时间内的登录尝试并返回可重试的 `too_many_attempts` 错误和需要等待的秒数，且不校验密码。等待时间随失败次数增长并有上限。系统 MUST NOT 永久锁定账号。

#### Scenario: 免费次数内
- **WHEN** 某用户名的连续失败次数未超过免费次数
- **THEN** 系统正常校验密码

#### Scenario: 超过免费次数后过早重试
- **WHEN** 某用户名的连续失败次数已超过免费次数，且在等待时间结束前再次登录
- **THEN** 系统返回 HTTP 429 和 `too_many_attempts` 错误，包含等待秒数，即使密码正确也不登录

#### Scenario: 等待结束后重试
- **WHEN** 等待时间结束后用户提交正确的密码
- **THEN** 系统登录成功，并清零该用户名的失败计数

#### Scenario: 换 IP 不重置计数
- **WHEN** 攻击者从不同 IP 对同一用户名连续登录失败
- **THEN** 所有失败计入同一个计数

#### Scenario: 用户名不存在
- **WHEN** 对不存在的用户名连续登录失败
- **THEN** 系统的计数和响应与已存在的用户名相同，不透露用户名是否存在

#### Scenario: 不永久锁定
- **WHEN** 某用户名长时间没有新的失败尝试
- **THEN** 失败计数过期，该用户名恢复为正常校验

### Requirement: 设备令牌
系统 SHALL 在登录成功后通过 `HttpOnly` Cookie 下发长期有效的随机设备令牌，并绑定到该用户。登录请求携带属于该用户名的有效设备令牌时，系统 MUST 使用这台设备单独的失败计数，而不是该用户名的公共计数。

#### Scenario: 常用设备不受攻击影响
- **WHEN** 用户名的公共计数正处于等待时间内，用户在曾登录成功的浏览器上提交正确的密码
- **THEN** 系统正常校验密码并允许登录

#### Scenario: 设备令牌属于其他用户
- **WHEN** 登录请求携带的设备令牌属于另一个用户名
- **THEN** 系统按没有设备令牌处理，使用公共计数

#### Scenario: 设备上的失败
- **WHEN** 携带有效设备令牌的登录连续失败超过免费次数
- **THEN** 系统对这台设备的后续尝试返回 `too_many_attempts`，公共计数不受影响

#### Scenario: 无效或过期的设备令牌
- **WHEN** 登录请求携带的设备令牌不存在或已过期
- **THEN** 系统按没有设备令牌处理

### Requirement: 认证请求按来源限流
系统 SHALL 按客户端 IP 限制登录和注册请求的速率，超出时 MUST 返回 HTTP 429 和可重试的 `rate_limited` 错误，且不把请求交给应用处理。客户端 IP MUST 按“识别真实客户端地址”的规则认定；同一 IP 的限额 MUST NOT 因为请求被分到不同的接入实例而放大。

#### Scenario: 同一 IP 频繁请求
- **WHEN** 同一 IP 在短时间内发出超过允许次数的登录或注册请求
- **THEN** 超出的请求收到 HTTP 429 和 `rate_limited` 错误

#### Scenario: 其他接口不受影响
- **WHEN** 同一 IP 的认证请求已被限流，它访问其他接口或 WebSocket
- **THEN** 这些请求正常处理

#### Scenario: 多个新连接
- **WHEN** 同一 IP 每次请求都新建连接，连续发出超过允许次数的登录请求
- **THEN** 超出的请求同样收到 HTTP 429，与这些连接被分到哪个接入实例无关

#### Scenario: 不同 IP
- **WHEN** 一个 IP 已被限流，另一个 IP 发出登录请求
- **THEN** 另一个 IP 的请求正常处理

### Requirement: 受信任设备
每个用户 SHALL 最多有两台受信任设备：一台手机、一台电脑。设备类型 MUST 按登录时浏览器的 User-Agent 判断，平板算作手机。用户在某类设备上登录成功时，该类还没有受信任设备的，这台设备 MUST 成为受信任设备；已有受信任设备的，只有这台设备最近 30 天发出的聊天消息条数大于原受信任设备的 1.5 倍时，才 MUST 替换原设备，否则原设备保持受信任。除登录外，会话续期时也 SHALL 按同样规则重新判断。

#### Scenario: 第一台手机
- **WHEN** 用户第一次在手机上登录成功
- **THEN** 这台手机成为受信任的手机

#### Scenario: 手机和电脑互不影响
- **WHEN** 用户已有受信任的手机，又第一次在电脑上登录成功
- **THEN** 这台电脑成为受信任的电脑，手机仍然受信任

#### Scenario: 新手机用得不够多
- **WHEN** 用户已有受信任的手机 A，在手机 B 上登录，B 最近 30 天发的消息不超过 A 的 1.5 倍
- **THEN** A 仍是受信任的手机，B 不受信任

#### Scenario: 新手机用得足够多
- **WHEN** 用户已有受信任的手机 A，手机 B 最近 30 天发的消息超过 A 的 1.5 倍，B 再次登录或续期
- **THEN** B 成为受信任的手机，A 不再受信任

#### Scenario: 每类最多一台
- **WHEN** 用户在多台手机和多台电脑上登录过
- **THEN** 任何时候受信任的手机最多一台、受信任的电脑最多一台

### Requirement: 受信任设备续期会话
系统 SHALL 允许已登录用户在受信任设备上续期当前会话，续期后会话的剩余有效期重新变为完整时长，会话令牌 MUST 保持不变。当前会话所在设备不是受信任设备时，系统 MUST 拒绝续期并返回 `device_required` 错误，会话的有效期不变。已失效的会话 MUST NOT 被续期。

#### Scenario: 受信任设备续期
- **WHEN** 用户在受信任设备上请求续期当前会话
- **THEN** 会话的有效期重新变为完整时长，会话令牌不变，已建立的连接不受影响

#### Scenario: 非受信任设备
- **WHEN** 用户在不受信任的设备上请求续期
- **THEN** 系统返回 `device_required` 错误，会话的有效期不变

#### Scenario: 续期时成为受信任设备
- **WHEN** 不受信任的设备最近 30 天发的消息已超过同类受信任设备的 1.5 倍，此时请求续期
- **THEN** 这台设备先成为受信任设备，续期成功

#### Scenario: 会话已失效
- **WHEN** 已登出或已过期的会话请求续期
- **THEN** 系统返回未认证错误，不会因此产生新的有效会话
